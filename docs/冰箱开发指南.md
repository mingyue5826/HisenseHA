## 1. 五个接口

### 1.1 读：`/4.0/iot/devices/detail`

```json
{"deviceId": "86100c0090020020000000403a9c5d10:lb051600602j0093fe7d2a1",
 "partnerId": "1001"}
```

响应里 `payload.device.states` 是一个 **74 键的字典**，直接按 key 取值。
`originalState` 是 356 项逗号数组，**与 states 不是一一对应，不要解析它**。

### 1.2 写：`/4.0/iot/devices/execute`

```http
POST https://iot-aihome.hismarttv.com/4.0/iot/devices/execute
appKey: commonweb
X-Sign-For: base64(md5(body + appSecret))
```

```json
{
  "appVersion": "6.2.18.7",
  "header": {"messageId": "<uuid4>"},
  "payload": {
    "exclusionFlag": 1, "sourceType": 20,
    "customerId": "100000001", "partnerId": "1001",
    "deviceId": "<deviceId>",
    "actions": [{"command": "<命令名>", "params": {"<键>": {"value": "<值>"}}}]
  },
  "appType": 1, "sourceName": "smartlifeAppH5", "accessToken": "<token>"
}
```

小程序用 `sourceType=21` / `sourceName=miniProgram` / `appType=2`，**两种都能打通同一后端**，
集成里沿用 `20/smartlifeAppH5/1` 即可。

**成功的响应会顺带回传完整 `states`**，可直接刷新实体，省一次 detail 请求。

### 1.3 错误码就是诊断工具

| 返回 | 含义 | 下一步 |
|---|---|---|
| `SUCCESS` | 命令名 + 参数 + 设备能力全对 | 写进白名单 |
| `paramError` | **命令名对**，参数键或取值错 | 换参数键 |
| `commandDuplicate` | **命令名对**，参数键匹配到多个子命令 | 用更精确的参数键 |
| `notSupported` | **设备命令表里没有这个命令名** | 换命令名，**不等于设备没这个功能** |

### 1.4 `layout/smartHomeApp/control` 是什么

返回 27 个栏目的 UI 描述（204 个 tile），**里面没有任何 states、没有任何 command**。
它能提供的只有文案：标题、`briefIntro`、`modelCombFunction.subFunction`。

⚠️ **它按产品模板返回，不等于本机硬件**。最直接的证据：本机有"制冰"栏目
（`IceMakerSwitch`，brief「开启后，将进行自动制冰」），但**这台冰箱实际没有制冰功能**。
所以 layout 只能用来拿文案，**不能用来判断能力**。

### 1.5 ★ 首页功能清单：`/4.0/iot/devices/function/getHomepageConfig`

请求体（`payload.products` 按产品型号查，可一次传多个）：

```json
{"appVersion":"7.0.8.12","payload":{"sourceType":20,
 "products":[{"productCode":"LB051600602J","categoryCode":"connector.device.type.fridge"}]},
 "appType":"1","header":{"messageId":"<uuid>"},"accessToken":"***",
 "deviceId":"<App 会话 ID，与设备 ID 不同>"}
```

返回**该机型在首页上的功能声明**，每条自带命令名、参数键、取值范围、状态映射。

这是 **App 拿到的"这台机器有什么功能"的正式声明**，按 `productCode` 返回，
响应很小（本机 9 条）。每条功能自带三样东西：

| 字段 | 用途 |
|---|---|
| `action.command` + `action.params[].attribute` | **命令名与参数键，官方写法** |
| `attributes[].value` | **取值范围**（数值型给区间，枚举型给选项与 `code`/`name`） |
| `states[].code` → `attribute` | 状态键与属性的对应关系 |

本机（`LB051600602J`）**全量只有这 9 条**：

| # | 功能 | command | params 键 | 状态键 |
|---|---|---|---|---|
| 1 | 食材管理 | — | — | — （纯入口，无 action） |
| 2 | 智能模式 | `SetModes.Smart` | `smartModeSwitch` | `workMode.Smart` |
| 3 | 冷冻室温度控制 | `SetTemperature.Freeze` | `freezeSetTemperature` | `setTemperature.freeze` / `displayTemperature.freeze` |
| 4 | 冷藏室温度控制 | `SetRefrigeratorTemperature` | `refrigeratorSetTemperature` | `refrigeratorSetTemperature` |
| 5 | 速冷模式 | `SetModes.QuickCooling` | `quickCoolingModeSwitch` | `workMode.QuickCooling` |
| 6 | 冷藏室温度控制（另一份） | `SetTemperature.Refrigerator` | `refrigeratorSetTemperature` | `setTemperature.refrigerator` / `displayTemperature.refrigerator` |
| 7 | 模式（总） | `SetModes` | `modes`（`optional=0`） | `workMode` |
| 8 | 冷冻室温度控制（另一份） | `SetFreezeTemperature` | `freezeSetTemperature` | `freezeSetTemperature` |
| 9 | 在线状态 | —（只读） | — | `onlineStatus` |

**两个结论**：

1. **同一功能会有两个名字**（#3/#8、#4/#6）。所以"从名字推命令"必然踩坑——
   同一份官方数据里就并存 `SetTemperature.Freeze` 与 `SetFreezeTemperature`。
   **以带后缀的全名为准**（#3、#6），旧别名（#4、#8）不用。
2. ⚠️ **这份清单只覆盖首页，不是完整能力表**。变温空间和除菌都能正常控制，
   却都不在这里（它们不在首页）。所以：
   **表里有 → 一定有；表里没有 → 不能断定没有。**
   判断"本机有没有 X"的正确顺序见 2.7。

**取值范围（来自 `attributes[].value`）**：

| 属性 | 区间 | 含义 |
|---|---|---|
| `refrigeratorSetTemperature` | `[2, 8]` | 冷藏设定温度 |
| `freezeSetTemperature` | `[-25, -15]` | 冷冻设定温度 |
| `displayTemperature.refrigerator` | `[0, 15]` | 冷藏当前生效温度 |
| `displayTemperature.freeze` | `[-40, -10]` | 冷冻当前生效温度 |
| `refrigeratorRelativeTemperature` | `[1, 6]` | 相对温差档（1..6 档） |
| `freezeRelativeTemperature` | `[1, 10]` | 相对温差档（1..10 档） |

`modes` 枚举本机只有两项：`0 = Smart`、`3 = QuickCooling`。

`preferFunctions` 是首页展示排序 + 条件渲染：`onlineStatus=0` 时**只显示在线状态**，
其余功能不展示。本集成按同一思路做离线降级，见 [5.1](#51-离线降级)。

**`attribute.type` 直接决定 HA 平台**（做数据驱动实体时用它，别靠键名猜）：

| type | 取值形态 | 对应 HA |
|---|---|---|
| `1` | `"[min,max]"` 数值区间 | `number`（可写）／`sensor`（只读） |
| `3` | `0/1` 开关（带 `Off`/`On` 枚举） | `switch` ／ `binary_sensor` |
| `4` | 枚举列表（`value`/`code`/`name`） | `select` |
| 无 `action` | 只读 | `sensor` / `binary_sensor` |

### 1.6 `scenes/execute/config/get`：命令表 + 冲突表

这个接口给的是"场景可用的设备动作"，本机 `commands` **只有 3 条**：

| command | 参数键 | 取值 | 状态键 |
|---|---|---|---|
| `SetTemperature.Refrigerator` | `refrigeratorSetTemperature` | type 1，`[2,8]`，后缀 ℃ | `setTemperature.refrigerator` |
| `SetTemperature.Freeze` | `freezeSetTemperature` | type 1，`[-25,-15]`，后缀 ℃ | `setTemperature.freeze` |
| `SetModes` | `modes` | type 4，`0=智能` / `3=速冷` | `workMode` |

注意这两条是**带后缀的全名**，与 1.5 的 #3/#6 一致；而 1.5 的 #4/#8 是旧别名。
集成代码用的正是带后缀的全名，✅ 与官方一致。

⚠️ **同一个"模式"参数有三个名字**，跨接口不统一：
`modes`（本接口 + 功能表 #7）／`smartFridgeModes`（冲突表里出现）／
`smartModeSwitch`、`quickCoolingModeSwitch`（单模式开关）。
混用会触发 `Matched multiple sub commands`。**做单模式开关时用后者，别用前两个。**

`conflictCommands` 是**互斥表**（双向成对出现），说明"预设模式"与"手动温度/档位"不能共存：

| 命令 A | 与命令 B 的哪些取值互斥 |
|---|---|
| `SetTemperature.Refrigerator` | `SetModes` ∈ `{0, 3, 4}` |
| `SetTemperature.Freeze` | `SetModes` ∈ `{0, 2, 6, 7, 8, 9}` |
| `SetRefrigeratorGear` | `SetModes` ∈ `{0, 3, 4}` |
| `SetFreezerGear` | `SetModes` ∈ `{0, 2, 6, 7, 8, 9}` |

代入本机的 `0=智能`、`3=速冷`，得到一条**可执行的规则**：

- **智能（0）同时锁住冷藏和冷冻设温**
- **速冷（3）只锁冷藏设温，不影响冷冻**

> 表里出现的 `2/4/6/7/8/9` 本机没有，是其它机型共用的模板值，忽略即可。
> `SetRefrigeratorGear` / `SetFreezerGear` 也不在本机 `commands` 里 ——
> 又一次印证"档位控制是别人家的能力"。

**双向都实测过**：开智能/速冷后该舱温度被锁（设定值不变、`displayTemperature` 被覆盖）；
手调温度后模式自动退出（见 3.3）。

## 2. `states` 74 键

### 2.1 值只有三种

| 值 | 含义 |
|---|---|
| `"0"` / `"1"` | 布尔量（`1` = 开/异常） |
| 数字字符串 | 温度、档位、频率 |
| `"--"` | **该键当前无有效值**。布尔位 = 机型不支持；枚举位 = 当前没有这个状态（如 `workMode` 无模式运行时） |

> `workMode` 就是典型的枚举位：`"0"` = 智能、`"3"` = 速冷、`"--"` = 无模式。
> 所以 `"--"` 不能一律读成"不支持"。

### 2.2 温度有 4 套前缀，别混

| 前缀 | 语义 | 用途 |
|---|---|---|
| `refrigeratorSetTemperature` / `freezeSetTemperature` | **设定**温度 | number，可写 |
| `setTemperature.refrigerator` / `.freeze` | 设定的点号别名 | 与上面同值，勿混用于 params |
| `refrigeratorRealTemperature` / `freezeRealTemperature` | **实测**温度 | sensor |
| `displayTemperature.refrigerator` / `.freeze` | **当前生效**温度（受控温度） | sensor（主） |

> `displayTemperature` 不是"面板显示"，是**当前真正执行的目标温度**。
> 开智能模式时：设定 6℃，`displayTemperature` 变 5℃；开速冷时：变 2℃。
> 换句话说，模式会覆盖设定值，而 `displayTemperature` 反映覆盖后的结果。

### 2.3 整机 / 模式 / 抽屉

| 键 | 语义 | 备注 |
|---|---|---|
| `onlineStatus` | 云连接 | `1`=在线 |
| `refrigeratorOn` | 运行开关 | `1`=运行；**只读**，无控制命令 |
| `compressorFrequency` | 压缩机频率 Hz | `0`=停机 |
| `workMode` | 模式总编码 | `0`=智能 / `3`=速冷 / `--`=无模式 |
| `workMode.Smart` | 智能模式位 | 布尔，跨机型稳定，优先用它 |
| `workMode.QuickCooling` | 速冷模式位 | 布尔，跨机型稳定 |
| `variationTempSpaceDrawer` | 变温空间档位 | `0`原鲜 / `1`0℃养鲜 / `2`母婴 |

> **`workMode.*` 的子键集合 = 该机型的模式清单**。本机正好 `["Smart","QuickCooling"]`。
> 这是多机型最有用的一个信号（见 4.4）。
>
> `workMode` 总编码与子键等价，但**编码值跨机型不统一**（本机 `0`/`3`，旧固件 `64`/`65`），
> 所以读状态只用布尔子键。

### 2.4 除菌（3 个键是同一功能的备选名）

`degermingSwitch` / `cleanerSwitch` / `dBDDegerming`

layout 第 18-21 栏把这三个名字用**逗号并列**写成候选，云端只认 **`dBDDegerming`**：

| 键 | 手动开除菌后 | 手动关后 | 结论 |
|---|---|---|---|
| `dBDDegerming` | `1` | `0` | **实际运行状态位，控制与状态两个实体都绑它** |
| `cleanerSwitch` | `1` | 仍为 `1` | 独立位（净味），不跟除菌同步 |
| `degermingSwitch` | `0` | `0` | 恒 0，本机不用 |

**一条命令同时启动除菌和净味**：`DBDDegerming` 参数 `dBDDegerming=1` 执行后，
`dBDDegerming` 与 `cleanerSwitch` 一起变 `1`，也就是离子除菌和净味是一起跑的。
所以控制实体命名为「除菌+净味」，不叫「除菌」。

除菌是"运行一次"的流程型功能（App 显示"本月已运行 34 次"），
所以它的状态会自己从 `1` 回到 `0`，不是长期开关；而且除了手动开启，
设备也可能按内部计划自动运行。因此分成两个实体：

| 实体 | 平台 | 用途 |
|---|---|---|
| 除菌+净味 | `switch` | **控制入口**：手动开/停一轮 |
| 除菌运行中 | `binary_sensor` RUNNING | **只读状态**：现在是否在跑（含自动运行） |

两者绑同一个键，所以值一致；分开是因为语义不同 —— 自动化里想判断"是否正在除菌"
应该读只读状态，而不是去读一个可写的开关（容易误以为开关是被人为打开的）。

`cleanerSwitch`（净味）单独做成只读 `binary_sensor`：它只有 `0`/`1` 两态
（`--` 表示机型不支持），但和除菌不是同一件事 —— 关掉除菌它不会跟着回 `0`，
所以不能拿来判断"正在除菌"。

> **为什么放在 `switch` 而不是 `button`**：它绑的是 `dBDDegerming`
> 这个**运行状态位**，所以既能下发（开/停），也能如实反映"现在正在除菌"。
> 跑完一轮后设备把它置 `0`，开关随轮询自动回到关闭 —— 这是真实状态，
> 不是 UI 假象。代价是要等一次轮询（60 秒）才会翻回去。
> 正因如此，`execute` 返回成功后设的乐观值只保 8 秒（`PENDING_CONTROL_TTL`），
> 之后一律以云端回读为准。若只需要"是否在跑"这一个只读信号（例如设备自己
> 按计划启动的场合），用并存的「除菌运行中」`binary_sensor`，不必读开关。

### 2.7 ★ 怎么判断"这台机器有没有这个功能"

这是本项目最容易错的地方。四种证据的可靠性完全不同：

| 证据 | 能证明什么 | 例证 |
|---|---|---|
| 命令实测 `SUCCESS` | **确定有**（最强） | 除菌 `DBDDegerming` 实测成功 |
| **在 `getHomepageConfig` 功能表里** | **确定有** | 9 条功能都在表里 |
| 值 = `--`（布尔位） | **确定不支持** | `wideOverTempAlarm=--` → 无宽温室 |
| 值 = `0` | **什么都证明不了**（可能只是默认值） | 本机无制冰机，`iceMakerWaterLackAlarm` 仍为 `0` |
| layout 有栏目 | **什么都证明不了**（产品模板） | 本机有"制冰开关"栏目，却没有制冰机 |
| **不在功能表里** | **什么都证明不了** | 变温空间、除菌都不在首页功能表，却能正常控制 |
| `workMode.X` 子键存在 | 弱证据，用来生成模式清单 | 本机只有 2 个模式位，实际也只支持 2 个 |
| 实物确认 | 强证据 | 制冰"没有" |

结论：
1. **功能表能证明"有"，不能证明"没有"**——它只覆盖首页，其他页面的功能不在里面。
2. 布尔位的 `--` 是唯一能单边证伪的字段；`0` 和"表里没有"都不算证据。
3. 判断"有没有"的可靠路径：**先在功能表找 → 再看 `--` → 最后实测一条命令**。

## 3. 已确认的命令（唯一可信清单）

### 3.1 命令表

| 动作 | command | params |
|---|---|---|
| 冷藏设温 | `connector.device.command.SetTemperature.Refrigerator` | `{"refrigeratorSetTemperature":{"value":"5"}}` |
| 冷冻设温 | `connector.device.command.SetTemperature.Freeze` | `{"freezeSetTemperature":{"value":"-16"}}` |

| 速冷模式 开 / 关 | `connector.device.command.SetModes.QuickCooling` | `{"quickCoolingModeSwitch":{"value":"1"}}` / `"0"` |
| 变温→原鲜 | `connector.device.command.SetVariationTempSpaceDrawer` | `{"variationTempSpaceDrawer":{"value":"0"}}` |
| 变温→0℃养鲜 | 同上 | `{"variationTempSpaceDrawer":{"value":"1"}}` |
| 变温→母婴 | 同上 | `{"variationTempSpaceDrawer":{"value":"2"}}` |
| 除菌+净味 开 | `connector.device.command.DBDDegerming` | `{"dBDDegerming":{"value":"1"}}` |
| 除菌+净味 关 | 同上 | `{"dBDDegerming":{"value":"0"}}` |

以上全部来自 App / 小程序真实抓包，并已实测返回 `SUCCESS`。

> 除菌是唯一**不带 `Set` 前缀**的命令，别照 `SetXxx` 规律去猜。
> 之前的 `SetDegermingSwitch` / `SetCleanerSwitch` / `SetDBDDegerming` 全部是错的。

除上表写法外，`SetTemperature`（裸名）+ 同样的参数键也实测通过，两种都可；
但**裸名同时前缀匹配 `.Refrigerator` 和 `.Freeze`**，靠参数键才区分得开，
一旦参数键写错就报 `commandDuplicate`（Matched multiple sub commands）——所以**优先用全名**。
集成代码现在用的就是全名，与 1.6 的命令表一致。

### 3.2 命名规律**不能外推**（关键）

把全部已确认命令摆在一起，出现 **5 种不同变换**：

| 字典 `function` | 实际 `command` | 实际 `params` | 变换方式 |
|---|---|---|---|
| `TemperatureControl.Refrigerator` | `SetTemperature.Refrigerator` | `refrigeratorSetTemperature` | 留后缀 |
| `Modes.Smart` | `SetModes.Smart` | `smartModeSwitch` | 留后缀 |
| `Drawer.VariationTempSpace` | `SetVariationTempSpaceDrawer` | `variationTempSpaceDrawer` | 后缀挪词尾 |
| `RefrigeratorTemperatureControl` | `SetRefrigeratorTemperature` | `refrigeratorSetTemperature` | 前缀挪词首 |
| `DBDDegerming` | `DBDDegerming` | `dBDDegerming` | **原样，无 Set** |

params 也有五种写法：`xxxSwitch` / `xxxModeSwitch` / `xxxSetTemperature` / `xxxDrawer` / `dBDXxx`。

> 所以**任何"从字典自动推导命令名"的方案都不成立**。
> 唯一可靠的路径：抓包，或实测。

### 3.3 六个固件行为（均已实测）

1. **开模式会锁定该舱温度**：开智能后，设定值保持 6/-16 不变，但
   `displayTemperature` 变为 5/-18（智能的固定值）；开速冷后冷藏变为 2℃。
   即**模式覆盖设定**，而 `displayTemperature` 反映覆盖结果。
2. **手调温度会退出模式**：速冷运行中调冷藏温度到 5℃，`workMode` 立即变成无模式，
   两个模式位归 0，冷冻温度保持速冷时的 -16 不变。
   按 1.6 的互斥表，范围并不对称：
   - 冷藏设温 → 退出 `Smart(0)` 和 `QuickCooling(3)`
   - 冷冻设温 → **只退出 `Smart(0)`**；`QuickCooling` 与冷冻设温不互斥
3. **关模式就是同一条命令发 `"0"`**，没有单独的"退出"命令：
   `SetModes.Smart` / `SetModes.QuickCooling` 的 value 改成 `"0"` 即退出，
   `exclusionFlag` 仍是 `1`。App 里那两个模式本来就是 on/off 开关。
4. **"记住原来的温度"不需要字段，设定值本身就是记忆**：模式运行期间
   `refrigeratorSetTemperature` / `freezeSetTemperature` **一次都没变过**，
   被覆盖的只有 `displayTemperature`。所以一关模式，`displayTemperature`
   自动回落到设定值。
   → 推论：HA 里 `number`（设定温度）在模式运行时不跟着变是**正确**的，
   它就是用户当初手动设的那个值；想看到"现在实际执行几度"要看生效温度传感器
   `displayTemperature`。两根管子别合并成一个实体。
5. **`execute` 成功会回传 states**，可直接 `async_set_updated_data`，不必再读一次。
6. **`workMode` 的 `--` = 无模式**，不是"不支持"：
   `"0"` 智能、`"3"` 速冷、`"--"` 无模式。旧固件这边是 `64`/`65` 的编码，
   所以**读状态用布尔子键**（跨机型稳定），不要用总编码。

## 5. 实体映射（当前）

| 数据 | 平台 | 分类 |
|---|---|---|
| 实测温度 ×2 | `sensor` | 主 |
| 设定温度 ×2 | `number` | 主 |
| 变温档位 / 工作模式 | `select` | 主 |
| **除菌+净味**（控制） | `switch` | 主 |
| 告警位 ×N（含 4 个门未关） | `binary_sensor` PROBLEM | 主 |
| 在线 / 运行 | `binary_sensor` CONNECTIVITY / POWER | 主 |
| 除菌运行中（`dBDDegerming`） | `binary_sensor` RUNNING | 主 |
| 净味（`cleanerSwitch`） | `binary_sensor` RUNNING | 主 |
| 压缩机频率 | `sensor` Hz | 主 |
| 生效温度 ×2 | `sensor` | 主 |
| 上次数据更新时间 | `sensor` TIMESTAMP | 诊断（`reportTime`，缺失退回本地读取时刻） |

> **冰箱只有「上次数据更新时间」一个实体归诊断，其余全在主（控制）分类**：设定
> 温度、工作模式、变温空间、除菌+净味都是日常要动的项，放进配置区只会多点一次。
> 判定标准不是"能不能改"，而是"要不要天天看"。

> **不再单独建「门」实体**：`refriOpenDoorAlarm` 这类键名字面就带 alarm，
> 语义是固件的门未关告警，不是一个独立的门磁读数。同一个值建两个实体
> （`门-冷藏室` DOOR + `告警-冷藏室门未关` PROBLEM）只会让主区出现重复卡片，
> 所以统一由告警位承载，`门未关` 就是 14 个告警位里的一个。
> 自动化判断"门开着"直接看 `告警-冷藏室门未关` 的 `on` 状态。

> **「除菌+净味」与「除菌运行中」同键不同用**：前者是 `switch`，手动开/停一轮；
> 后者是只读 `binary_sensor`，回答"现在是否在跑"（含设备自动运行）。两者值一致，
> 但自动化里判断状态应读后者，避免把"开关开着"误读成"有人手动开的"。

> **机型没有的告警位是"禁用"而不是"永远灰着"**：16 个告警实体先全建（保证离线
> 启动不缺），读到 `states` 里明确为 `"--"` 的再写注册表 `disabled_by=integration`。
> 本机 16 个里 11 个属于这种，禁用后主区只剩 5 个真实告警位。详见 §5.1。

> **`entity_category` 与实体平台是两回事**：`DIAGNOSTIC` 不是"另成一个平台"，
> 它只是给实体打个标记，让 HA 把卡片折叠进设备页的「诊断」区。
> 判定标准是**要不要主动盯着看**：门有没有关、有没有超温、压缩机停没停、
> 现在执行几度 —— 这些是设备运行状态，放主区；只有排查故障时才看的
> （更新按钮、洗衣机协议快照）才标 `DIAGNOSTIC`。

**工作模式为什么还留在 `select` 而不是拆成两个 `switch`**：模式之间互斥
（开一个另一个必被云端关掉），两个独立开关会造出"都开"这种设备上不存在的状态，
而且开 A 关 B 时要连发两条命令。用 `select` 只有一个"当前值"，
选项 `智能 / 速冷 / 自定义` 正好对应三种合法状态：

- 选 `智能` / `速冷` → `SetModes.*` 发 `"1"`
- 选 `自定义` → 对当前正在跑的那个模式发 `"0"`（就是"手动退出模式"）

所以"手动关闭速冷"在 HA 里就是下拉框选一下"自定义"，和 App 里退出模式等价。
`current_option` 由 `workMode.Smart` / `workMode.QuickCooling` 两个布尔位推出来，
不读总编码。已经是自定义时再选"自定义"不会下发任何命令（幂等）。

未做实体：28 个非官方故障位（只解析、不建实体）、`hydropeniaAlarm`（语义未证实）。

### 5.1 离线降级

判断"能不能用"只看一道闸：

| 闸门 | 判据 | 生效结果 |
|---|---|---|
| 设备是否在线 | `states.onlineStatus == "0"` → `status["online"] is False` | 离线 → 除 connectivity 等例外外全部 `unavailable` |

**云端读取失败（超时、token 失效、网络不通）不参与可用性判断**：实体保留上一次读到的
值继续显示。把整屏实体变灰并不会多提供任何信息，反而让"集成坏了"和"设备离线"混成
一谈；后者由 `onlineStatus` 准确表达。机型根本不报 `onlineStatus` 时 `online` 为
`None`，**按可用处理**，不能当成离线，否则这类机型会一个实体都不剩。

各实体自己还会判断"本机是否上报这个键"（`status[key] is None`），缺失时显示
`unavailable` 而不是 `0`/`off`。

例外只有三个：`connectivity` 实体、`force_update` 按钮、`上次数据更新时间` 传感器
设了 `_attr_available_offline`。连通性实体必须在离线时仍能显示"离线"，否则它自己也
变 `unavailable`，等于把结论藏起来；手动刷新按钮是断网时唯一的自救入口；
更新时间实体本身就是用来告诉你"手上的数据有多旧"的，它跟着变灰就没意义了。

**离线时不能解析 `states`**（这是关键）。设备离线时 `detail` 返回的是云端缓存：
告警位可能被写成 `0`、部分键整段缺失、甚至全部变 `--`。照常解析会得到两个错误结论——
"所有告警都正常"和"这些功能都不支持"。所以 `onlineStatus == "0"` 时只更新 `online`
一个字段，其余保持上次在线时的值，由上面那道闸统一屏蔽。恢复在线后以云端真实值覆盖。

`reportTime`（设备层字段，不在 `states` 里）是这条规则唯一的例外：**离线时照常更新**。
设备离线后它停在最后一次上报的时刻，正好回答"这份数据到底有多旧"—— 冻住它反而
会让这个诊断实体失去意义。实体取值优先用它，机型不报时退回本机成功读取的时刻。

实体在 setup 阶段**不等第一次读取**，否则离线启动（或首次读取超时）会让实体永久缺失：

- `binary_sensor` 的 16 个告警实体一律先建出来，读到完整 `states` 后再按值分流：

| `states` 里的值 | 含义 | 处理 |
|---|---|---|
| `"0"` / `"1"` | 机型支持 | 正常显示 |
| `"--"` | 机型**明确没有**这个功能 | 立即 `unavailable`，并写入实体注册表 `disabled_by=integration` |
| 键不存在 | 本次响应不完整 | 只 `unavailable`，**不禁用**，下次完整响应自动恢复 |

  本机 16 个告警键里 **11 个是 `"--"`**（只剩 5 个真实位），所以"不支持就禁用"
  不是可选项：留着就是 11 个永远灰着的卡片。

  禁用有三道保险：只在 `"--"` 时做、已经有 `disabled_by` 的条目一律不碰（你手动
  启用过的不会被集成再关掉）、只写一次。注册表变化会让 HA 立刻把该实体从状态机
  移除，不用重载；代价是这个判断**不可自动回退** —— 固件升级后真的支持了，需要
  到实体设置里手动启用一次。
- 除菌 `switch` 仍要等 `degerming_active` 出现才建：它对机型只有"有/没有"两种，
  建了就是一个可点的开关，给没有该功能的机型留一个永远灰着的开关并不划算。

**什么时候会真的变成 unavailable**：

| 设备 | 刷新方式 | 说明 |
|---|---|---|
| 冰箱 | **60 秒定时轮询**（`_FRIDGE_SCAN_INTERVAL`） | 门没关、除菌跑完、压缩机停机都不会触发用户操作，必须主动拉；设备上报云端本身有约 1 分钟节流，轮询更快也拿不到更新数据 |
| 空调 / 洗衣机 | 事件驱动，不轮询 | 操作都发生在 HA 里，控制成功后 1 秒回读，没必要白耗请求 |

两台设备之外还会在 HA 启动/集成重载、点「强制更新」按钮时刷新。所以冰箱掉线
最迟约 1 分钟能发现，空调则要等下一次操作或手动刷新。

#### 怎么验证

**限速模拟不了离线** —— 限速只是让请求变慢，连接最终还是会成功。要测只能真的断。

| 想测的 | 在路由器里怎么做 | 预期现象 |
|---|---|---|
| 云端读不到 | 给 **HA 主机**断网（关闭它的上网权限/拉黑，不是限速） | 请求按 aiohttp 默认超时失败，3 次尝试间隔 60 秒；**实体不会变 `unavailable`**，继续显示上次的值，只有「上次数据更新时间」停止前进 |
| 设备离线 | 给 **冰箱**断网（关闭它的上网权限/拉黑），HA 主机保持正常 | 点一次「强制更新」→ 除 connectivity 外全部 `unavailable`，connectivity 显示 `关闭` |

第二种是核心逻辑（`onlineStatus=0`），第一种现在只影响数据新鲜度、不影响可用性
（云端读不到不再把整屏变灰，见 §5.1）。测完记得把权限恢复。

不联网也能跑的一半：`python docs/check-offline-fallback.py`，用真实抓包验证解析层、
`available` 的各分支、告警禁用的三道护栏和 `reportTime` 记录，覆盖上面两种场景的
状态迁移（需要 `cryptography`）。

### 5.2 翻译文件（`strings.json` + `translations/`）

实体名全部来自 `translation_key`，三个文件必须同步：

| 文件 | 作用 | 内容 |
|---|---|---|
| `strings.json` | hassfest 校验用的翻译源 | 与 `translations/en.json` **完全相同** |
| `translations/en.json` | 英文，运行时读取 | — |
| `translations/zh-Hans.json` | 简体中文，运行时读取 | — |

加一个实体时两件事一起做：

1. 代码里写 `translation_key="fridge_xxx"`；
2. 在 `entity` 下**对应平台**加 `"fridge_xxx": {"name": "..."}`，英文进 `strings.json`
   和 `translations/en.json` 两份，中文进 `translations/zh-Hans.json`。

漏了不会报错，只是 UI 上直接显示 key 本身（像 `fridge_xxx`），很难看但能跑。
动态生成的告警 key 是 `fridge_alarm_<states 键名>`，16 个都要有。

改了 `translations/en.json` 就同步 `strings.json`，两者不一致时 hassfest 会报错。
本机验证：`python docs/check-translations.py`（见脚本内说明）。

## 6. 怎么补一条新命令

### 6.1 抓包（唯一可靠的办法）

**App 抓包已打通**（手机 root + 系统证书），比小程序更全：

1. 海信爱家 App 进入冰箱页 → 点目标功能
2. 抓 `POST /4.0/iot/devices/execute`，记 `payload.actions[].command` 和 `params`
3. 若不确定有没有这个功能，先抓 `POST /4.0/iot/devices/function/getHomepageConfig`
   看首页功能表；**表里没有不代表没有**，还需要看 `states` 的 `--`
4. 填进 `docs/probe-commands.py` 的 `COMMAND_CANDIDATES`，跑 `--try` 回归一次

小程序仍可作备用渠道（抓到的命令名一样能用，请求风格按集成的 App 风格发）。

> 接口的请求头、签名、请求体格式见
> [`接口文档-AIHome（海信爱家）.md`](./接口文档-AIHome（海信爱家）.md)。

### 6.2 探针脚本是什么

`docs/probe-commands.py` 不是读取工具，它会**真的向你的冰箱下发控制命令**，
然后把云端返回的错误码翻译成结论（`SUCCESS` / `paramError` / `notSupported`）。

```bash
python probe-commands.py <账号> <密码> --list          # 只看候选，不下发
python probe-commands.py <账号> <密码> --try "<命令名>" '{"<键>":{"value":1}}'
python probe-commands.py <账号> <密码> --run --only mode   # 批量，会逐条下发
```

依赖 `cryptography`。`--list` 不需要账号，`--run` 前会要求按回车确认。

单条 `--try` 只发一条命令、打印结果就退出，**适合验证一个具体猜测**。
